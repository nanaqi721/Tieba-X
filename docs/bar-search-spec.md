# 贴吧关键字搜索规格

## Problem Statement

用户目前无法根据贴吧名称发现相关贴吧，也无法在匹配结果较多时持续滚动浏览。未登录用户同样需要使用该能力，并需要看到足以判断贴吧活跃程度的头像、名称、关注数和帖子数。现有贴吧计数同时存在数据库基数与 Redis 未落库增量，因此搜索必须明确使用稳定、一致的数据来源来排序、展示和生成游标。

## Solution

提供一个允许匿名访问的贴吧搜索接口。用户输入贴吧搜索词后，系统在 MySQL 中查找名称包含该搜索词的可发现贴吧，并按数据库中的关注数、帖子数和贴吧 ID 依次降序返回。接口采用不透明复合游标滚动分页，默认每次返回 10 条，并允许客户端持续请求全部匹配结果。

## User Stories

1. 作为未登录访客，我想按贴吧名称搜索贴吧，以便在注册或登录前发现感兴趣的社区。
2. 作为已登录用户，我想获得与访客一致的搜索结果，以便搜索排序不受登录状态影响。
3. 作为搜索用户，我想让输入先去除首尾空白，以便无意输入的空格不影响匹配结果。
4. 作为搜索用户，我想在贴吧名称包含完整搜索词时命中，以便通过部分名称找到贴吧。
5. 作为搜索用户，我想让英文名称匹配不区分大小写，以便输入大小写不同仍能找到目标贴吧。
6. 作为搜索用户，我想让 `%` 和 `_` 表示普通字符，以便特殊字符不会意外扩大匹配范围。
7. 作为搜索用户，我想在搜索词为空或超过 20 个 Java 字符长度单位时收到明确的参数错误，以便及时修正输入。
8. 作为搜索用户，我想只看到正常且未删除的贴吧，以免发现封禁或已移除内容。
9. 作为搜索用户，我想优先看到关注数更多的贴吧，以便先发现更受关注的社区。
10. 作为搜索用户，我想在关注数相同时优先看到帖子数更多的贴吧，以便进一步按活跃内容量排序。
11. 作为搜索用户，我想在关注数和帖子数都相同时按贴吧 ID 降序获得稳定顺序，以便结果可以可靠地进行游标分页。
12. 作为搜索用户，我想在每条结果中看到贴吧 ID、名称、头像、关注数和帖子数，以便展示搜索卡片并跳转到贴吧详情。
13. 作为搜索用户，我想让无头像贴吧返回空头像值，以便客户端统一展示默认头像。
14. 作为搜索用户，我想默认每次加载 10 条结果，以便首屏响应保持轻量。
15. 作为客户端开发者，我想在 1–10 范围内设置每页数量，以便不同界面可以控制批次大小。
16. 作为客户端开发者，我想只保存和回传一个不透明游标，以便无需理解关注数、帖子数和贴吧 ID 的组合规则。
17. 作为客户端开发者，我想获得 `hasMore` 和 `nextCursor`，以便准确决定何时继续加载。
18. 作为客户端开发者，我想在末页或无匹配结果时获得空游标和 `hasMore = false`，以便停止滚动请求。
19. 作为接口使用者，我想让损坏、字段缺失或与搜索词不匹配的游标返回参数错误，以免静默回到第一页造成重复内容。
20. 作为系统维护者，我想让排序值、返回计数和游标值都来自数据库，以便三者保持一致并避免把 Redis 实时增量混入稳定分页。
21. 作为系统维护者，我接受翻页期间数据库计数变化导致的少量重复或遗漏，以便无需为每次搜索维护快照。
22. 作为系统维护者，我想只精确开放新的搜索接口，以便创建、删除、关注和取消关注等写操作继续受到登录保护。

## Implementation Decisions

- 修改 `bar-server` 以提供 `GET /api/bars/v1/search`，并扩展贴吧控制器、服务和 Mapper 接口。请求参数为必填 `keyword`、可选 `cursor` 和可选 `pageSize`。
- 贴吧搜索词先调用 Java `String.strip()` 去除首尾空白，再使用 `String.length()` 校验长度必须在 1–20 之间。缺失、空白或超长输入均抛出项目现有的客户端参数异常。
- 只匹配贴吧名称，不匹配描述或帖子内容。匹配语义为名称包含完整搜索词；依赖现有 MySQL 大小写不敏感排序规则实现英文不区分大小写。
- 在进入 SQL 前依次转义 `!`、`%`、`_`，Mapper 查询使用显式转义字符，使 `%` 和 `_` 只表示自身。
- 数据源为 MySQL `bar` 表。搜索显式限定正常状态和未软删除记录，不依赖自定义 XML 查询自动应用逻辑删除条件。
- 排序、响应中的关注数与帖子数、以及游标中的计数全部直接使用 `bar` 表冗余字段。搜索路径不读取或叠加 Redis 未落库增量。
- 排序为关注数降序、帖子数降序、贴吧 ID 数值降序。后续页使用与该顺序一致的词典序 keyset 条件：关注数更小，或关注数相等且帖子数更小，或前两者相等且贴吧 ID 更小。
- Mapper 每次请求 `pageSize + 1` 条；服务层用额外一条判断是否仍有下一页，并只向客户端返回 `pageSize` 条。
- `pageSize` 缺省值为 10，有效范围为 1–10。非数字、整数溢出或越界沿用项目参数错误行为，不进行静默截断。
- 第一页允许不传游标；空字符串或纯空白游标按未传处理。
- 游标是 Base64URL 编码的不透明 JSON，至少携带数据库关注数、数据库帖子数、贴吧 ID 和规范化搜索词摘要。编码方式沿用现有帖子搜索，不增加 HMAC 签名。
- 搜索词摘要由规范化搜索词的小写形式生成，用于阻止同一游标被用于其他搜索词。游标无法解码、字段缺失、字段类型非法或摘要不匹配时返回参数错误。
- 返回模型使用独立的贴吧搜索结果和贴吧搜索项类型，不修改现有基础贴吧返回类型，避免影响已有批量查询及服务间调用。
- 成功响应数据包含 `records`、`nextCursor` 和 `hasMore`。每条记录包含字符串类型的 `barId`、`name`、可空 `avatarUrl`、`followerCount` 和 `postCount`。
- 只有确实存在下一页时才返回非空 `nextCursor`；空结果和末页返回 `nextCursor = null`、`hasMore = false`。接口不计算或返回总匹配数。
- 参数与游标错误沿用项目异常约定：HTTP 200，业务码 `A0001`。成功响应继续使用项目统一结果包装。
- 在 gateway 的匿名白名单中精确加入新搜索路径；在 `bar-server` 登录拦截器中仅对白名单内该路径的 GET 请求放行。不能使用 `/api/bars/**` 形式扩大匿名权限。
- 匿名与登录请求执行完全相同的查询，不读取用户上下文、不提供个性化排序，也不返回是否已关注等用户态字段。
- 直接使用 MySQL，不引入 Elasticsearch、全文搜索服务或缓存搜索结果。可为正常状态、逻辑删除、关注数、帖子数和贴吧 ID 添加与筛选/排序一致的复合索引；该索引不能消除包含匹配对贴吧名称的扫描，需在接近十万级数据量时通过真实数据验证执行计划。
- 分页采用弱一致性，不建立搜索快照。数据库计数在两次请求之间变化时允许少量重复或遗漏。
- 规格假设贴吧 ID 在数据库中是 BIGINT 雪花 ID，并继续在 Java/API 层以字符串表示，避免 JavaScript 数字精度损失。

## Testing Decisions

- 好测试只断言外部可观察行为：HTTP 契约、参数错误、匹配结果、排序、分页边界、游标兼容性和权限结果；不直接断言私有方法或具体序列化实现细节。
- 主要测试缝隙为贴吧搜索服务的公开方法，使用可控 Mapper 返回值覆盖规范化、转义、`pageSize + 1`、游标生成/校验和响应组装。这一层不需要连接 Redis，并应验证搜索流程不会用 Redis 增量改写返回计数。
- HTTP 契约使用 MockMvc 覆盖请求参数解析、统一响应结构、字符串贴吧 ID、可空头像，以及参数异常映射。优先沿用现有帖子搜索控制器测试的组织方式。
- Mapper 行为需要使用包含同关注数、同帖子数、不同 ID、封禁记录和软删除记录的数据集，验证完整三字段降序与三段 keyset 边界。若当前测试环境无法运行 MySQL Mapper 集成测试，至少保留一项针对真实 MySQL 的验证步骤并记录执行计划。
- 网关测试验证未携带登录态的搜索请求被放行，同时相邻的贴吧写接口仍被拒绝；`bar-server` 拦截器测试验证仅 GET 搜索路径匿名放行，其他方法和路径权限不变。
- 关键字测试覆盖缺失、空字符串、纯空白、长度 1、长度 20、长度 21，以及按 `String.length()` 计算的代理对边界。
- 匹配测试覆盖大小写差异、名称包含、仅描述包含不命中，以及字面量 `!`、`%`、`_`。
- 分页测试覆盖缺省页大小、自定义 1 和 10、0、11、非数字及整数溢出。
- 游标测试覆盖未传/空白为第一页、合法下一页、无下一页、非法 Base64、非法 JSON、缺字段、非法字段类型和搜索词摘要不匹配。
- 顺序测试至少覆盖：关注数不同；关注数相同而帖子数不同；前两者相同而贴吧 ID 不同；游标恰好位于每一类并列边界。
- 结果测试覆盖无匹配、少于一页、恰好一页、多于一页、末页，以及 `avatarUrl = null` 原样返回。
- 使用模块级 Maven 测试命令验证 `bar-server` 及其依赖，并运行 gateway 相关测试验证双层匿名白名单。

## Out of Scope

- 不搜索帖子标题、帖子正文或贴吧描述。
- 不返回总匹配数，不提供页码/偏移量分页。
- 不叠加 Redis 未落库计数，不提供实时排行榜。
- 不保证一次滚动会话的快照一致性。
- 不引入 Elasticsearch、MySQL FULLTEXT 或其他专用搜索基础设施。
- 不提供拼音、同义词、分词、模糊纠错或搜索建议。
- 不提供个性化排序、当前用户是否关注、搜索历史或搜索结果缓存。
- 不扩大任何现有写接口或非搜索接口的匿名权限。
- 不修复现有帖子删除路径对贴吧帖子数增量使用错误标识的问题；该问题属于独立数据一致性缺陷。

## Further Notes

- 现有帖子搜索已经提供相近的关键字规范化、不透明游标、`records/nextCursor/hasMore` 响应和参数错误约定，应复用其行为和命名，但贴吧搜索的游标排序键改为关注数、帖子数和贴吧 ID。
- 当前数据库定义仅为贴吧名称提供唯一索引。包含匹配无法通过普通 B-tree 直接定位名称；选择直接查询 MySQL 是基于近期规模不超过约十万贴吧且暂无严格响应时间 SLA 的前提。
- 当前帖子删除流程疑似使用帖子 ID 而非贴吧 ID 写入帖子数减量缓冲。搜索将按约定忠实返回数据库计数，但该既有问题可能导致部分贴吧帖子数本身不准确，建议单独建缺陷处理。
- 本功能决策均易于局部调整，未达到“难以逆转、缺少背景会令人意外、存在重大权衡”三个 ADR 条件，因此不新增 ADR。
